# BC-100 avg@3, scoring, and fixed retry selection

The original core campaign is `bc100-r3-hermes-parity-v3`; its first pass contains 3,000 planned question/repeat/harness/strategy observations. The recovery campaign `bc100-r3-hermes-parity-v3-retry1` has a frozen 963-entry `retry-ledger.json`. Previously completed original predictions remain selected. For every ledger member, the recovery attempt is selected regardless of whether it finishes, scores better, or scores worse. A retry is not a fourth repeat. No selection depends on the judge's score.

`judge_bc_v3_completed.py` uses the repository's actual Hermes BrowseComp judge prompt and parser, with an added strict numeric score 0/1 validation. It grades completed predictions only, on exact route `deepseek-v4.1-flash-1017/zijian/sfb`, independently recorded from prediction model routes. There is no route fallback. The four-concurrent-request core judge watches both source roots; request and response artifacts are private under `outputs/grading/bc100-v3-deepseek-sfb-v1`, outside all native workspaces. Gold answers appear only in judge artifacts and the frozen grading cohort, never in prediction specifications. Each grade binds the attempt path and result SHA. A dispatched request without a durable result remains unknown and is never automatically resubmitted. Explicitly invalid judge output remains missing.

Judge raw provider usage, cached-field presence, non-cache input, output, total, conservation, returned model alias, and HTTP wall time are recorded per request. Missing cached input is not zero. The returned alias `deepseek-v4-1-flash-261017` is the observed provider string; it does not independently verify backend weight equivalence. Gateway dollar pricing is unknown. Judge usage is separate from prediction usage and must not be silently added to a method's prediction-only cost.

`report_bc_v3_scored.py` watches these grades and produces `summary.md`, CSV, JSON and question-hash-only observation files in the grading output's `analysis/` directory. It always publishes first-pass and fixed-retry-selected views separately. The report requires all 100 questions in a repeat before calling its fraction accuracy, and all 100×3 outcomes before mean ± sample standard deviation and confidence intervals are considered ready. Missing completed grades and unknown/interrupted/not-started predictions remain missing with lower/upper accuracy bounds. Explicit terminal failed/timeouts with confirmed cleanup count zero operational success; this is recorded separately from a judged wrong answer.

Confidence intervals resample the 100 question clusters, averaging the three repeats within each question. VERA and each baseline are paired on question and repeat; a two-sided sign-flip test uses question-level mean differences. Holm correction is reported only when all eight planned comparisons (four per harness) are ready. Repeated interim significance is not published. A non-significant p-value does not establish equivalence, and repeat labels alone do not prove independent random seeds.

**Recovery adds conditional resources.** Since the retry set includes timeout and budget failures, recovered accuracy is not a single-attempt fixed-budget result. Report original first-pass metrics alongside the recovered selection. Resource analysis must sum original and recovery prediction tokens/time for every retried question, including unsuccessful work; selecting only the retained attempt's cost would understate spending. Unresolved usage remains missing. The report states this policy explicitly; it does not invent missing cumulative costs or dollar prices.

The initial four-request judge pilot was valid HTTP 200/JSON score output, with 1,831 prompt and 394 output tokens (2,225 total), explicitly reported cached input zero and no conservation errors. This pilot validates the scoring pipeline, not benchmark accuracy. The durable core judge and report watches are recorded in their respective `watch-service.json` files.
